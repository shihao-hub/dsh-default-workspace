## AI 写的代码到底能不能信？——Bob 大叔用确定性工具取代逐行检查

**来源**：抖音 @大小飞 ｜ 视频 [7691653099139632424](https://www.douyin.com/video/7691653099139632424) ｜ 时长 16:17
**对谈双方**：《代码整洁之道》(Clean Code) 作者 Robert C. Martin（Bob 大叔）× TypeScript 教育家 Matt Pocock

---

### 一句话结论

Bob 大叔说自己**完全不看 Agent 写出来的任何代码**——不是躺平信任 AI，而是把「逐行审查」换成了**确定性工具构成的验证体系**：复杂度检查、变异测试、架构约束、多 Agent 流水线。生成速度被拉高之后，人类真正该守住的是**组织复杂性、判断质量、识别 Agent 何时开始挣扎**这三件事。

### 背景：他经历了什么

- 1964 年（12 岁）写下第一个程序，18 岁做第一份程序员工作，至今编程超过 50 年。
- 去年圣诞节前后开始认真用 AI 编程工具（ChatGPT、Grok），最初并不惊艳；找 Agent 写代码「写得不太行，但确实写出来了」。
- 早期阶段他一直在**给 Agent 擦屁股**：速度快，但总留隐患，反而拖慢了自己——「有意思，但让人沮丧」。

### 转折点：把两个搁置二十年的想法捡回来

他意识到：既然 Agent 这么快、又不在乎枯燥，那它可以做**人类根本做不到的事**。

1. **CRAP 分数**——把测试覆盖率与每个函数的圈复杂度合成一个分数，衡量函数到底有多糟。2000 年代初跑过一次，找出了一堆烂函数，但只能一个个改、还要重写测试，成本太高而搁置。
2. **变异测试（mutation testing）**——程序自动改坏你的源码（把负号改正号、小于改大于），每次改动跑一遍完整测试；测试**本该失败**，如果没失败就出现了一个「存活的变异体」。以前要跑一整晚，同样没法进日常流程。

**现在**：交给 Agent 跑。原本一整晚的变异测试，**30 分钟完成**。Agent 写代码会留下碎屑和浮毛，但它们自己也是清理这些东西最好的工具。

### 为什么不用「堆提示词」而用「确定性工具」

- 他试过写提示词引导：把 TDD 方法、整洁代码要求都写进去，最后得到一份**长达十页**的文档告诉 Agent 什么是好代码。
- 结果发现模型对待规则的态度**特别像《加勒比海盗》里的海盗法典**——听起来是规则，对它们来说更像一堆建议。
- 技术原因：**Lost in the middle**。上下文窗口越大，最前和最后的内容更容易被关注，夹在中间的内容容易被忽略、甚至像消失了一样。第 3 句记得清清楚楚，第 50、80 句就被丢到角落了。
- **确定性工具不会这样**——不会因为规则写在第 50 行还是第 80 行就把它当建议。
- 所以关键手法是：**把初始提示词精简到绝对最小值**，尽量留在高优先级区域，之后交给确定性工具。
- Matt 补充了「上下文窗口的**聪明区**和**愚蠢区**」这一说法：上下文越长，注意力机制越吃力，信息被逐渐稀释，像一间越来越拥挤的房间，每个 token 都在大声说话，最后很难从噪音里分辨信号。

**代价与平衡**：确定性工具会明显拖慢 Agent——你把它放进循环里，不断改代码直到工具说 OK：加测试、降圈复杂度、拆函数，要很久才能达标。存在一个「检查过多」的临界点：如果慢到不如人类，你就输了。他目前观察能维持 **2–4 倍生产力优势**，本质是用一部分生产力换更高的代码质量。

### 烂代码问题：Agent 一样会撞墙

- 一直让 Agent 往下做而不清理烂摊子，它**会越来越慢**：改一处破坏另一处，为修那处又破坏第三处，最后原地绕圈。
- 代码烂到一定程度 Agent 就处理不了了，**他甚至遇到过一个 Agent 直接说「我处理不了了」**。

### 他现在的多 Agent 流水线

一个任务按角色串起来，每个 Agent 在**干净的上下文窗口**里开工：

1. **规格定义器**——把人类写的文档转成 Gherkin 语言和 QA 流程
2. **编码器**——写单元测试、实现故事逻辑，让 Gherkin 测试跑通
3. **清理器**——复杂度分析与常规代码审查
4. **强化器**——跑变异测试，反复验证测试是否真的有效，确保 100% 覆盖率
5. **QA Agent**——把书面 QA 文档转成可执行脚本，直接操作系统，给出确定性结果

对比：单个 Agent 给个任务 **5 分钟**就完成，但结果是否可靠很难说；走完整套流程可能要**1 小时**，但依然划算——**人类做同样的工作可能要半天**。多 Agent 的另一个好处是能并行，且单一聚焦任务能缓解 Lost in the middle；代价是启动开销（一个 Agent 可能要 10–15 秒才理解上下文）。

### 架构：不靠人盯，靠工具约束

- 之前一个多月他**手动**做模块结构设计：让 Agent 先构建，再不断追问「这里的结构是什么」「模块之间怎么关联」，得到令人恐惧的答案后亲自设计划分与通信方式——非常辛苦。
- 于是他让 Agent 造了两类工具：
  - **架构查看器**：屏幕上弹出类似 UML 的图，展示模块结构与依赖关系，可点击下钻到子模块甚至直接看代码。
  - **依赖规范工具**：定义哪些模块**应该**依赖哪些、哪些**绝对不能**互相依赖，形成一份 **Agent 无法违反的规范文件**；违反了就必须用反转依赖、提取接口等方式修复。
- Matt 提到 John Ousterhout 的**深层模块**概念——接口简单、内部隐藏大量信息，对 Agent 极其理想，因为它们只需读接口而不必理解实现。Bob 认同：模型非常关注**接口的名称和结构**，这意味着它们不必读下层代码——既是优势也是风险。

### 传统规范要怎么改

| 项目 | 调整 |
|---|---|
| **CRAP 阈值** | 从人类的 **≤4** 放宽到 **6**，甚至考虑提到 **8**（覆盖率 100% 时，CRAP=6 意味着该函数有 6 条执行路径且每条都被测到） |
| **TDD** | 曾经是坚定拥护者，但那是**为人类思维演化出的纪律**，不打算强加给 Agent。逼 Agent「一行测试一行生产代码」没有意义；即使强制，它们最终也总会回到「先写代码再写测试」。他更愿意允许 Ousterhout 式的做法——**先写函数再写测试** |
| **价值观** | 纪律可以松动，**价值观必须守住**——只是阈值要按 Agent 的特点重设 |

### 关于前期规划：别掉进「超长规格」的陷阱

- 他认为当下最大的诱惑是**过度编写规格说明**：不断完善需求与计划，再一次性交给 Agent。这是源自 70 年代的老诱惑，瀑布流开发就是典型，而敏捷的兴起很大程度上是对它的反思。
- 他自己试过，**一次次被证明是灾难**：Agent 无法完全按你的计划执行——你不可能提前想到所有细节，Agent 也没有你那么强的判断力，很容易朝错误方向一路跑偏，最后只能叫停、回滚、重新计划。
- 于是他回到敏捷方式：先让 Agent 完成一两个具体任务，看整体架构有没有问题，必要时手工介入调整，再让它继续。他怀疑**最后这一步人工组织永远无法完全摆脱**。
- 对流行的**规格驱动开发**，他的直觉是这条路行不通：Agent 非常喜欢写计划，会不断修饰得越来越华丽完美、细节越来越丰富，但真正执行时往往还是崩盘。
- **一美元盖房的比喻**：假设改一栋房子的成本只要一美元（打地基、修屋顶、之后所有修改都只要一美元），你会先花几千美元请建筑师设计一套完美方案、再一次性盖出来吗？还是直接走到承包商面前说「地基打这里，做成这个形状——不对，改一下，厨房放这边，客厅放那边」？显然后一种更合理。**既然软件修改的成本已接近零，为什么还要花大量精力做昂贵的前期规划？**（他也提醒：这些 spec 是转瞬即逝的，会消失、会频繁变化，不等同于源代码。）

### 给新生代开发者的忠告（全场最值得深思的部分）

Matt 提出 Ousterhout 的**战术编程 vs 战略编程**之分：战术像地面作战的士官，战略像指挥整场战争的将军。问题是 **Agent 非常擅长战术，却非常不擅长战略**。既然 AI 吞掉了大量战术性工作，新人该怎么学战略？

Bob 坦言没有完美答案，但给了路径：

1. **先老老实实写代码**——至少写一年，才能真正知道 Agent 到底在处理什么。
2. **进公司后先被当作一个 Agent 对待**——那位手下跑着一堆 Agent、自己负责战略决策的首席工程师，应该给你分配和 Agent 一样的任务，让你接受和 Agent 一样的确定性工具约束，在这种状态待上几个月。产出会很低，但能学到非常多。
3. **通过这场严酷考验后**，也许才会被信任去亲自运行一个 Agent。
4. **不能完全丢掉代码**——就像他十年前常说的：如果从没写过汇编，就该花一个周末写写汇编，才能知道底层到底发生了什么；整天只写 Java 就是生活在一个幻觉世界里。今天这条依然成立。这条路是：**二进制 → 汇编 → C 这样的基础语言 → Python 这样的高级语言 → 处理 Agent 的工作 → 学会用确定性工具 → 在监督下战略性运行 Agent**。
5. **读老书**——Tom DeMarco、Ed Yourdon 的著作，以及《程序员修炼之道》。很多重要经验恰恰是七八十年代总结出来的，需要过滤过时内容，但核心依然适用。

**怎么判断 Agent 在犯错？** 他说早先他靠看代码、发现坏代码，但那其实不是最重要的部分；**更重要的是看着 Agent 挣扎**——作为程序员他自己经历过同样的挣扎，所以能看出来。问题在于刚入行的人**根本识别不出这种挣扎**，他是靠艰苦的时间才学会的。

### 收尾：软件基础非但没过时，反而更重要

- 引用「**软件是人类迄今为止尝试过的最复杂的东西**，比我们做过的任何其他事情都要复杂」。基础是我们组织复杂性的一种方式，让复杂的东西变得可以理解——**不仅是让人类理解，也让模型理解**，毕竟模型终究是模仿人类建立起来的。
- 那些认为软件基础已经不重要的人**会吃到苦头，而且不会等太久**（可能比他想象的更久一点）。Agent 确实很厉害，但**他已经见过它们撞墙**，他知道那堵墙就在那里。
- 每次抽象层向上提升——从二进制到汇编、汇编到编译器、编译器到模型——处在更低层级的人都会抱怨「这会毁了一切，我们都没工作了，编程变得这么简单，五岁小孩都能写代码了」。**每次都是同样的故事，但同样的规则依然适用。**
- **你今天扔掉的那些规则，一年之后很可能还是要从地上把它们捡起来**，重新想起为什么当时需要它们。

---

> 这套实践的本质不是在说 AI 不行，也不是说传统方式是万能的。它说的是：当代码生成速度被大幅提升之后，**组织复杂性的能力、判断代码质量的能力、以及识别 Agent 何时开始挣扎的能力**——这些更高层面的东西非但没有过时，反而变得更加重要了。
